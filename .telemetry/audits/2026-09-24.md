# Tracking Audit: 2026-09-24

**Codebase:** little-log-pwa, origin/main `036bb308`, live `little-log-v350`
**SDK:** none. First-party only.

Cubby emits no behavioural events. It measures in two ways: a handful of signals written
specifically to measure (acquisition, page counts, operational health), and a funnel
reconstructed after the fact from records the product already stores to do its job.

## Derived measures

`tools/analytics.js` (185 lines) and `tools/funnel.js` (131 lines) read Firestore with the admin key
and reconstruct per-household measures from product data. Run by hand.

| Measure | Derived from |
|---|---|
| created | `households.createdAt` |
| firstLog | earliest care-log timestamp in the household |
| activeDays | distinct days carrying a care log |
| members | `households.members` keys |
| babies | `households.app.babies` |
| invited / joined | `invites`, `members > 1` |
| pro | `waitlist` |

Funnel stages, nested: Signed in, Added a baby, Logged something, Came back (day 2+), Sticky (7+ days).
Reported alongside: time to activation, invite-to-join, retention, the two-people wedge.

In Cubby's data model `events` are care logs (feeds, sleep, nappies) held for the product's own
function. The funnel's measures of activity are timestamps on those logs.

**Collections the funnel reads:** users, households, feedback, waitlist, events (collectionGroup), invites.
**Collections it does not read:** `households/{hid}/pregnancy/{owner}`, `mhealth/{owner}`, photos, notes, pageStats,
pushLedger, campaigns, newsletter, D1 subscribers, D1 games/guesses/hubs.

## Identity Management

| Call type | Present | Details |
|---|---|---|
| identify() | NO | Identity is the Firebase Auth uid. No analytics identity layer. |
| group() | NO | The household `{hid}` is the natural group: ownerId, members map, one shared care log. |
| page()/screen() | Server only | pageStats counts HTML navigations. The app is one SPA, so in-app screens are not counted. |
| reset()/logout | Partial | Sign-out clears localStorage including cubby-acq and cubby-ref (`store-firebase.js:2492`). |

The household is a two-level group hierarchy in practice (household, then babies or a pregnancy
within it), with membership that changes over time.

## Observed Patterns

- **Naming style:** mixed. camelCase collections (`pageStats`), kebab-case storage keys (`cubby-acq`), snake_case log tags (`pagestats_fail`).
- **Naming format:** free-form. No event names exist, so no convention exists.
- **Centralization:** none on the client. Server-side page counting is centralized at the single asset-serving choke point, `worker.js:2017-2022`, which is the one clean pattern in this inventory.
- **Error handling:** server writes are fire-and-forget via `waitUntil`, with `console.error` on failure. Client writes are try/catch and swallow.

## Observations

- **Pregnancy and trying-stage households.** Their journey is stored in `households/{hid}/pregnancy/{owner}`, an
  owner-owned collection. The funnel reads 0 fields from it (`grep -c 'preg|ttc|stage' tools/analytics.js` = 0),
  while `app/store-firebase.js` carries 60 references. The funnel's second stage is
  `households.app.babies.length > 0`, so a pregnancy household is counted as signed in and not at
  any later stage.
- **Nothing between page load and a stored record.** The funnel sees a household when it exists and
  when a care log exists. Actions that do not produce a stored record, such as opening the invite
  sheet, reaching a step of the first-run wizard, or viewing the Pro sheet, leave no trace.
- **pageStats is anonymous by construction.** No user id, cookie or IP is stored, and secret-bearing
  path segments are collapsed before storage.
- **Acquisition is first-touch and stamped once.** `cubby-acq` is written only if absent and copied
  only onto a user doc that does not yet exist. An invited caregiver joining an existing household is
  not given an `acq`.
- **The scheduled report has not produced output since 2026-08-30.** `launchd` job
  `com.cubby.weekly-health` is loaded and fires on schedule. Its log's last six lines are
  `fatal: Unable to read current working directory: Operation not permitted`, and the job exits 0.
  The repo lives under `~/Downloads`, a folder macOS privacy controls do not let a launchd agent read.
  Newest file in `~/cubby-reports`: `weekly-2026-08-30.md`.
- **Operational failures are visible only live.** Every `console.error` above goes to the Cloudflare
  log stream, which retains nothing unless `wrangler tail` is attached at the time.
