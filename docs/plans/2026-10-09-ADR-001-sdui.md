# ADR-001: Server-driven UI, or configuration over anchored widgets

**Status:** Proposed

**Deciders:** the founder

**Progress, 10 October:** action item 1 is done (acd61c21: Pro date moved to January 2027 in 26

## Context

The question: should Cubby be cleaned up and rebuilt as server-driven UI (SDUI), so screens are
configured and managed without app releases, on a robust design system with anchored widgets, with
Pro launching in January 2027?

What is true today, measured from this tree on 9 October 2026:

- **App releases are already not needed for UI.** `capacitor.config.json` sets
  `server.url: https://little-cubby.com/app/`. The iOS and Android shells load the live PWA, so a push
  to main reaches web, iOS and Android at once. Only native plugin changes need a store build.
- **But every change costs a deploy.** A push runs the full pre-push suite (about 45 minutes) and
  several sessions push to main concurrently. A one-word copy fix or a kill switch waits in that queue.
- **The UI is 19.5k lines in one file.** `app/index.html` holds 1,317 functions, 204 render/open
  functions, 153 sheets, 885 inline handlers and 2,082 hand-written `class="` templates. Components
  are copied, not shared.
- **The design system is real but stops at tokens.** `DESIGN.md` defines personality, 142 colour
  tokens, the type and stack contracts, spacing, shape, icons and voice, and 12 gates enforce them
  (type, stack, contrast, touch target, motion, surface token, component dupe and others). There is no
  component layer: nothing says "this is the alert pill" and renders it one way.
- **The home screen is hand-ordered.** `renderHome()` is about 200 lines of inline priority logic over
  hero, timer banners, alerts, nudges, tips, teach cues, quick log, wake window and offers.
- **The rendering pattern is unsafe by construction.** On 6 October an emulator repro showed a
  member-chosen document id running as script through `onclick="openEdit('${id}')"`. The fix is in
  progress (see the 6 October postmortem when it lands). Any UI driven by data from a server or from
  other members inherits this risk unless rendering is made safe first.
- **Pro is hard-coded and its date is already wrong.** `PRO_CFG`, `PRO_LAUNCH`, `PRO_TASTE` and
  `PRO_LOCK` are constants in `app/index.html`. Parents are told "launching October 2026" in the Pro
  sheet, the settings row and on `pricing/` (three places). It is 9 October and Pro is now January 2027.
- **Usage, read from production on 9 October 2026 (aggregate counts only).**
  - The daily funnel snapshot (D1, written on 16 of the last 16 days): 0 of 12 households logged
    anything in the last 7 days; no household created in the last 30.
  - Firebase Auth, 14 accounts: 2 opened the app in the last 30 days (token refresh), the latest on
    4 October; none signed in afresh in 30 days.
  - Household documents: none updated since 31 August.
  - Blind spots, so these are lower bounds on what the systems can see, not proof of zero: nothing
    counts app opens (Cloudflare serves pages without running the Worker, so the page counter only
    sees 404s); the founder's own accounts are not excluded (INTERNAL_UIDS unset); and the local weekly
    report has failed on every run since 30 August (macOS denies the job access to ~/Downloads).
  The constraint on the business still looks like activation and retention rather than UI delivery,
  but it needs an app-open measure before anyone leans on it.
- **Pro's critical path is not code.** UAE trade licence, then the Lemon Squeezy store, then deploying
  the already-built billing Worker. The licence has the longest lead time.

## Decision

**Do not rebuild Cubby as SDUI.** Build a small, typed **remote configuration** that drives a fixed
**registry of anchored widgets** and the Pro settings, on top of a **component layer** that is safe
by construction. Migrate screens into components when they are touched, never in one rewrite.

Config may choose, order, limit and word things. It may never carry markup or code. Widgets are code
that ships through the gates; config only refers to them by id.

## Options considered

### Option A: full SDUI rebuild

The server sends screen descriptions (JSON layouts); the client is a generic renderer.

| Dimension | Assessment |
|-----------|------------|
| Complexity | High: schema, renderer, versioning, offline cache, an authoring tool |
| Cost | The whole October to January window, and Pro slips |
| Scalability | Strong for many teams editing many screens; Cubby has one founder |
| Team familiarity | New infrastructure to own alone |

**Pros:** layouts change without a deploy; per-segment experiments become possible.
**Cons:** solves release friction Cubby does not have (the shell already loads live code). The
screens that matter most are local, offline and safety-critical logic (dose limits, the fever safety
net, loss holding, pregnancy privacy), which a layout schema cannot express, so code still ships for
every real change. It widens the injection surface the 6 October repro just showed. And it spends the
pre-Pro window on plumbing while retention is the actual problem.

### Option B: status quo

| Dimension | Assessment |
|-----------|------------|
| Complexity | None now, rising every week |
| Cost | Every copy or flag change pays a 45-minute deploy |
| Scalability | Poor: one 19.5k-line file edited by many concurrent sessions |
| Team familiarity | Full |

**Pros:** no new work.
**Cons:** stale facts reach parents (the Pro date today). No kill switch faster than a deploy.
Duplicated components drift. Inline-handler string templates keep producing injection bugs.

### Option C: configuration over anchored widgets, plus a component layer (chosen)

| Dimension | Assessment |
|-----------|------------|
| Complexity | Low to medium, in small shippable steps |
| Cost | About 8 to 10 weeks of focused work, alongside the Pro paperwork |
| Scalability | Enough for a solo founder; extensible if a team arrives |
| Team familiarity | Same stack: Firestore, plain JS, the existing gates |

**Pros:** instant copy, flag and kill-switch changes; Pro settings out of code before launch; the
home screen becomes a declared order of named widgets; safety widgets can be pinned so no config can
hide them; new UI is escaped by construction.
**Cons:** two sources of truth (code defaults plus config) need a schema and a gate; components are
adopted gradually, so old and new patterns coexist for months.

### Option D: rewrite in a framework (React, Svelte or similar)

Same timeline problem as A, plus a build step and a new runtime in a codebase with zero build today.
A plain-JS component layer gets most of the safety and consistency benefit without the rewrite.
Rejected for now.

## Trade-off analysis

The decisive trade-off is **what SDUI buys versus what Cubby lacks.** SDUI's main payoff, skipping
store review, is already in hand through `server.url`. What Cubby lacks is cheaper to get: changing
words and switches without a deploy, a predictable home screen, components that render one way, and
rendering that cannot be injected. Option C delivers those without moving product logic to the server.

The second trade-off is **time.** About 12 weeks remain before January. Option A consumes them all.
Option C ships value every two to three weeks and leaves room for the work that decides whether
Pro has anyone to sell to.

## Design of the chosen option

**1. Remote config (one document, read-only to clients).**
- Firestore `config/app`. Rules: any signed-in user may read; no client may write (the founder edits
  in the console or through an ops script). The SDK's offline cache already makes it work without a
  connection.
- Holds: feature flags and kill switches (today's `FEATURES`), Pro (`launch` text, checkout and portal
  URLs, price line, taste counts, lock lists), home anchor order and widget enablement, paywall copy.
- Every value has a default compiled into the app, so first run, offline and a broken document all
  behave exactly like today. The client validates against a schema and ignores any key or value it
  does not recognise.
- Strings from config are rendered only through escaping helpers, never into handlers.

**2. Anchored widgets (the home first).**
- Named anchors: `home.top`, `home.alerts`, `home.primary` (quick log), `home.secondary`,
  `home.footer`. Each widget registers `{ id, anchor, eligible(ctx), priority, render(ctx),
  locked }`.
- `renderHome()` becomes: for each anchor, take the eligible widgets, apply the config's order and
  limits, render.
- Widgets marked `locked` cannot be hidden or demoted by config: fever safety net, due-dose alerts,
  loss holding, running timers. This mirrors the "free forever" guardrail list in `PAYWALL.md`.

**3. Component layer.**
- Extract the most repeated patterns first: sheet header, chip row, settings row, toggle row, alert
  pill, card. Each takes props, escapes text and ids itself, and emits `data-action` attributes
  handled by one delegated listener instead of inline handlers.
- Adopt it when a screen is touched; never as a big-bang rewrite.

**4. Pro by January 2027.**
- Move every `PRO_*` constant into the config, keeping today's values as the defaults.
- Entitlement stays server-side: the billing Worker writes `households/{hid}.pro`; the client
  only reads it.

## Consequences

- **Easier:** correcting dates, prices and copy in minutes; switching a feature off without a
  deploy; reasoning about what the home screen shows; Pro launch day becomes a config change.
- **Harder:** two sources of truth that must agree (schema and gate required); a period where
  components and string templates coexist.
- **Revisit SDUI if:** a fully native (non-webview) app is built, a non-engineering team needs to
  author screens, or traffic is large enough to experiment on layouts.
